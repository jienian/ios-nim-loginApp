# 故障分析设计

这份文档记录 `ios-nim-loginApp` 诊断中心的分析方法，目的是让工程师能复核结论，而不是只看到一个百分比。

## 结论口径

App 输出的是**排序后的根因假设和证据强度评分**，不是已经证实的整机根因，也不是统计概率。最终确认仍需结合时间线复核、稳定复现、服务端/系统日志或换件验证。

## 数据来源

### 1. App 结构化事件

登录和注册流程会把真实交互写进本地事件日志（最多保留 100 条）：

| 事件 | 触发 | 关键属性 |
| --- | --- | --- |
| `auth.attempt` | 发起登录/注册 | `attempt_id`、`flow` |
| `auth.validation_failure` | 表单校验失败（账号格式、密码长度等） | `attempt_id`、`flow` |
| `auth.success` | 登录/注册成功 | `attempt_id`、`flow`、`duration_ms` |
| `auth.failure` | 凭据或账号类失败 | `attempt_id`、`flow`、`duration_ms`、`error_code` |
| `network.failure` | 非预期网络/服务错误 | `attempt_id`、`flow`、`duration_ms`、`error_code`、`underlying_error_type` |
| `auth.logout` | 退出登录 | 无敏感属性 |

约束：

- 密码从不写日志。
- 同一次尝试的 attempt / success / failure 共用一个 `attempt_id`。
- 消息中的账号只以脱敏形式出现，例如 `d***@nim.app`。
- 事件只保存在本机；当前版本不上报服务器。

### 2. 即时设备快照

一键收集时读取当下可观察的上下文：

- App 版本和 build
- 设备型号、系统版本
- `ProcessInfo` 热状态（serious / critical 时按 WARN 进入分析，nominal / fair 只作上下文）
- 电池电量、充电状态和低电量模式（模拟器可能没有读数，此时明确标为不可用）
- 系统运行时间和时区
- 可用存储空间

这些是上下文，不是自动生成的故障。若电池/热状态只是正常读数，不会形成故障假设。

### 3. 工程师导入的外部日志

诊断中心可从剪贴板导入日志文本。解析器支持本 App 导出格式，以及常见的：

```text
[ERROR] 2026-10-05T00:01:02Z auth: 登录失败：账号或密码不正确
2026-10-05 00:02:03 WARN [network] request timeout after 3000ms
INFO system: app launched successfully
```

外部日志是硬件、服务端或系统故障证据进入分析的主要入口。iOS 沙箱不能直接读取其他 App 日志、服务端日志或完整的系统级 sysdiagnose；当前版本不假装能做到。

### 4. 缺陷单

所选硬件缺陷单只提供部件先验和现象上下文。若日志没有形成证据链，分析只会输出低分的「相关异常（待验证）」，不会把缺陷标题直接当根因。

## 分析流水线

```text
事件采集 → 解析清洗 → 去重归并 → 多信号评分 → 证据复核 → 生成报告
```

1. **解析清洗**：统一时间戳、级别、分类、事件名和属性。
2. **去重归并**：把账号、UUID、毫秒数等易变值归一化后，折叠同一故障的重复日志；重复总次数保留为复发证据。
3. **良性过滤**：内容为健康、正常、检查通过、扫描完成或初始化成功的 INFO/WARN 行，不会因为提到电池、摄像头等部件而被误报为故障。
4. **多信号评分**：综合直接故障短语、日志级别、独立证据数、重复次数、时间线位置、缺陷部件一致性和恢复/反证。
5. **证据复核**：每个假设引用最多 3 条原始日志，并单独列出失败之后出现的成功/恢复记录。
6. **生成报告**：可导出 Markdown incident 报告，包含结论、假设排序、证据、反证、关键 WARN/ERROR 时间线、数据质量和原始日志。

## 评分方法

基础分 30 分，主要增减项如下（最终截断到 5–96）：

| 信号 | 影响 |
| --- | --- |
| 直接故障短语或明确错误码 | 每组 +18，信号项总上限 28 |
| 较弱故障上下文 | 每组 +8 |
| ERROR 证据组 | +14 |
| WARN 证据组 | +4 |
| 多条独立证据 | +4 |
| 同一故障重复出现 | 每次重复 +2，上限 8 |
| 重复至少 3 次且无恢复 | +5 |
| 故障位于时间线后段 | +4 |
| 与所选缺陷部件一致 | +6 |
| 失败后出现成功/恢复 | -7 |

低于 35 分的假设不会进入排序。缺陷单先验的待验证项固定为 25 分，不计为已证实根因。

例如：一次输错密码并随后登录成功，会被记录为认证事件；由于有恢复证据，它表示一次已解决的凭据失败，而不是持续的认证系统故障。若同一错误连续重复且没有成功，才会得到更高分。

## 当前覆盖的故障域

- 登录 / 认证
- 网络 / 服务端
- 散热 / 温控
- 电池 / 电源管理
- 摄像头
- 显示 / 触控
- 系统稳定性 / 看门狗

同一日志可能同时支持多个假设。例如「摄像头过热导致对焦失败」会同时进入温控和摄像头候选，报告会保留这种不确定性。

## 验证场景

单元测试覆盖：

- 登录失败被抓取、引用原始证据并识别后续成功为反证
- 登录失败结构化事件包含 `error_code` 和 `attempt_id`，且不包含密码
- 电池健康、摄像头初始化完成、屏幕扫描完成等良性行不误报
- 三次相同失败折叠为 1 条独立证据，但总出现次数和评分上升
- 认证与摄像头混合故障同时保留两个假设
- 导入的网络 timeout / 503 日志命中网络异常
- 本 App 导出格式和普通文本日志可以解析
- incident 报告引用证据并声明评分不是统计概率

## 已知限制与后续接入点

- 当前登录后端仍是 Mock；接入真实 API 后应把客户端 `attempt_id` 与服务端请求 ID 对齐。
- 尚未接入 MetricKit、崩溃上报后台、OSLog 导出、服务端日志或 sysdiagnose 专用解析器。
- 规则词表适合当前演示和常见日志，不等同于经过标注数据集训练/校准的诊断模型。
- 若要进一步提高可信度，应建立真实故障样本集，标注根因后统计 precision / recall，并按版本复测误报率。
